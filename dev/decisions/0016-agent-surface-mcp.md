# Agent surface: MCP

Status: Accepted  
Date: 2026-08-17

## Context

Notebook agents need a structured interface for reading, editing, running, checking, exporting, and inspecting data without depending on browser internals.

## Decision

Alder exposes an MCP JSON-RPC 2.0 server over line-delimited stdin/stdout, with an in-process session backend or a REST proxy backend. Each raw message is capped at 16 MiB and must be a valid UTF-8 JSON object with bounded structural complexity and unique keys at every depth. The transport rejects an invalid or ambiguous frame before dispatch and drains its line without poisoning the next valid request. MCP requests use scalar string IDs or exactly represented integer IDs in the inclusive binary64-safe interval ±(2^53-1), so every response can preserve its correlation key; null, fractional, compound, and out-of-range IDs are rejected before effects. Known MCP methods require named parameter objects, and initialization validates protocol version, capabilities, and client information before changing lifecycle state. A successful `initialize` request enters an awaiting-client-confirmation phase; only a valid `notifications/initialized` message enters normal operation, and only `ping` may execute before that transition. Notifications never emit a response, and invalid or out-of-phase notifications are effect-free. For a local notebook path, MCP resolves runtime metadata and layered configuration with the same precedence as the CLI/web Session, but it defers a configured startup run until the valid initialized notification; startup settles before normal operations and a transport/startup failure is surfaced by subsequent normal requests. `tools/call` requires a known, nonempty tool name and object-valued arguments; envelope/schema failures are top-level JSON-RPC parameter errors, while failures after a valid invocation reaches tool execution remain result-level `isError` values. Tools return compact JSON and resources expose source, DAG, and cell outputs. Run tools on either backend return only after the exact requested run and every deferred run-button reset it causes have reached a terminal state; ordinary R execution errors remain notebook state, not protocol errors, while reset failures retain their Alder error code. The URL adapter follows the bounded Session run journal through the narrow, read-only `/api/run-operation?run_id=` route instead of treating a generic idle observation as settlement. It sends an explicit `scope` discriminator to `/api/run`, so `run_all` remains global in lazy mode and `run_stale` remains selective in automatic mode; requests without a scope retain the editor's mode-sensitive behavior. For either backend, `set_widget` does not report success until its exact widget operation has succeeded and the automatic consumer run it schedules has reached an idle terminal state. The REST proxy follows the same bounded Session widget journal through the narrowly projected, read-only `/api/widget-operation?token=` status route; the route exposes only token, status, error, and causal reset metadata. An automatic/app `run_button` call additionally waits for its causally linked reset operation and verifies that the visible value is `FALSE`, so the next action cannot collide with a pending reset. That verification recursively locates named widgets inside output layouts and resolved lazy output, matching the browser and Session ownership rule. In lazy editor mode, `set_widget` returns after consumers have been marked stale; its reset remains intentionally deferred until a later explicit run, and that explicit run then owns and settles the reset. Widget-operation and reset failures retain and return their Alder error code.

## Consequences

Agent clients get one stable protocol surface. Every mutation must use existing notebook/session validation and errors must preserve Alder error codes in MCP responses. The Session retains bounded internal widget-token and run-id journals because output-local operation records may be replaced by a one-shot reset or an edited/re-executed widget owner before a protocol client can observe the original identity. The widget journal links an initiating run-button token to the reset token it caused. The run journal separately links every reset created when that exact run completes, including lazy resets deferred from an earlier widget action. Temporal adjacency and generic runtime-idle observations are not used as causality.

This decision is part of the full marimo parity implementation plan.
